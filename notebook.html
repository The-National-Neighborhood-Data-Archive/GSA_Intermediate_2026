1. What identifiers do you actually have?

About 6 minutes

Most survey and clinical datasets do not have geography. They have a string: an address, a city, a ZIP code, collected for mailing or billing and never checked for the job it is now being asked to do. That job is to place each person in a neighborhood that another dataset has measured.

Before any merge, answer three questions about that string:

  • Which identifier do I have? An address, a ZIP code, a Census code?
  • How complete is it? Rows with nothing to look up never match.
  • What is it an identifier of? A ZIP code is a mail route, not a place. An address is not an identifier until something turns it into one.

If your data already carry Census tract or ZCTA codes from an earlier geocoding step, you are ahead but not exempt. Those codes follow the boundaries of one census year, and the boundary question in Section 4 applies to them too.

What NaNDA is published at

NaNDA describes neighborhoods, not people. Every measure is a count, a density, or a rate for a geographic unit in a given year. There are no individual records in the archive, so the linking is on you. NaNDA cannot know where your participants live.

Today we use three datasets from the NaNDA catalog on ICPSR:

  • NaNDA: Social Services (1990–2022)
  • NaNDA: Parks (2018, 2022)
  • NaNDA: Socioeconomic Status (2008–2022, two files)

All three are released at the Census tract level and the ZCTA level. We use the ZCTA files, because ZIP codes are what the synthetic data can offer. Every file we join to is drawn on 2010 boundaries. Robert Melendez explains that choice in the session, and Section 4 shows what changes when you mix boundary years.

Our file has ZIP codes and NaNDA has ZCTAs. They look alike, usually the same five digits, and they are not the same thing. Section 3 is about that gap.

2. If you have addresses: geocoding

About 4 minutes. Explanation only; the code in this notebook stays on the ZIP-to-ZCTA route.

A street address is the most precise location most studies collect, and the least usable as it stands. Geocoding turns it into a point on the map. A spatial join then places that point inside a Census tract, and the tract-level NaNDA file joins on the tract code.

The route, step by step:

  1. Geocode. Send each address to a geocoding service and get back coordinates plus a precision code. The Census Bureau’s geocoder is free and returns the tract directly. tidygeocoder in R talks to OpenStreetMap, ArcGIS, Google, and others through one interface.
  2. Check precision. A rooftop match and a “somewhere in this city” match both come back with coordinates. Keep the tract only where the match is precise enough to trust. With OpenStreetMap, that is the place rank.
  3. Spatial join to 2010 tracts. Download the TIGER/Line tract boundaries for the census year your NaNDA file uses and intersect the points with them.
  4. Join to the tract-level NaNDA file on the tract code, then run the same diagnostics as Section 4.

Why we are not doing it live:

  • It is slow and it costs. Free services throttle to about one address per second. Paid ones charge per thousand addresses.
  • It is a terms-of-service question. Some services restrict storing or sharing the results, so a geocoded file may not be shareable even when the addresses are.
  • It fails differently. Addresses that will not parse, apartment-level ambiguity, and PO boxes all produce a coordinate or nothing, and the failure never looks like a join error.

The shape of it in R, using OpenStreetMap:

library(tidygeocoder)   # one interface to many geocoding services
library(tigris)         # Census boundary files
library(sf)             # spatial joins

mydata_geocoded <- mydata %>%
  geocode(street = address, city = city, state = state, postalcode = zip,
          method = "osm", full_results = TRUE)

# Keep a tract only where the match is precise enough (OSM place_rank >= 26).
points <- mydata_geocoded %>%
  filter(!is.na(lat)) %>%
  st_as_sf(coords = c("long", "lat"), crs = 4326)

tracts2010 <- tracts(state = unique(mydata$state), cb = FALSE, year = 2010)
points <- st_transform(points, st_crs(tracts2010))

mydata_tract10 <- st_join(points, tracts2010, join = st_intersects) %>%
  mutate(tract_fips10 = if_else(place_rank >= 26, GEOID10, NA_character_)) %>%
  st_drop_geometry()

From here the tract-level NaNDA files join on tract_fips10 exactly as the ZCTA files join on zcta10 below. Everything in Section 4 applies unchanged.

3. ZIP is not ZCTA

About 10 minutes

A ZIP code is a Postal Service artifact. It names a set of delivery routes. It exists to get mail to a door, not to describe a place.

  • Some ZIP codes are a single building.
  • Some are a bank of post office boxes with no residents.
  • Some cross county and state lines.
  • The Postal Service redraws them whenever the mail requires, without telling anyone doing research.

A ZCTA, a ZIP Code Tabulation Area, is the Census Bureau’s answer to the fact that researchers use ZIP codes anyway. For each decennial census, the Bureau assigns every census block to the ZIP code most of its addresses carry. The result is a set of areas with the same five-digit names as ZIP codes that tile the country and can be measured. NaNDA’s ZCTA files are built on these.

Most of the time a ZIP code and the ZCTA of the same name cover roughly the same people. Most of the time. ZIP codes with no ZCTA, such as post office boxes and single-site ZIPs, have nowhere to go. ZIPs mostly absorbed into a neighboring ZCTA are assigned there, under a different number. So the step from ZIP to ZCTA is a lookup against a crosswalk, not a rename of the column. And the crosswalk follows the boundaries of one census year, like everything else.

The crosswalk we’re using

  • UDS Mapper ZIP Code to ZCTA Crosswalk (2019 release, archived copy). Included in the ZIP as data/zip_to_zcta_2019.xlsx.
  • NaNDA’s published merge code: Chenoweth & Khan, code for merging NaNDA ZCTA-level datasets with the UDS Mapper crosswalk (2024).

Use the published merge code rather than a snippet copied from a screen. It is citable, it is maintained, and a fix lands in one place you can find again.

ImportantWhich ZCTA boundaries does your crosswalk produce?

The 2019 release of the UDS Mapper ZIP Code to ZCTA Crosswalk produces 2010-boundary ZCTAs. That makes it the right partner for NaNDA’s 2010-boundary files, which is what we use throughout. With your own data, read the crosswalk’s documentation for its target boundaries before anything else.

Who did you lose?

The table above is a headline, not a diagnostic. It tells you the size of the loss and nothing about its shape. The diagnostic is whether the rows that did not get a ZCTA differ from the rows that did, and it belongs here, before anything from NaNDA is attached.

In this file about 17% of rows have no ZIP at all. If those rows are disproportionately rural, older, or in worse health, the matched sample is no longer the sample you drew. Every neighborhood coefficient you estimate is then conditional on having a mailable address. That is a selection problem, and it does not announce itself.

Neither language does this for you. Isolate the rows without a ZCTA and put their means beside the others’ means on the variables the study is about.

4. Which boundaries? Joining, and checking the join

About 15 minutes

The join is three lines, and nobody gets the three lines wrong. If a column name is misspelled the software says so. What people get wrong happens on either side of those lines and can be easily missed.

  • Silent error 1: boundaries. ZCTA boundaries were redrawn for 2020. Most codes kept their five digits and changed their edges; some appeared, some vanished, some were split. A 2010 code joined to a 2020 file usually finds a row, and the row usually describes approximately the same place. Your regression will not carry a footnote saying which cases were approximate.
  • Silent error 2: never looking at what fell out. A left join keeps every row of your data and fills NaNDA’s columns with NA where nothing matched. An inner join drops those rows. Either way the analysis proceeds. Stata’s merge reports _merge. R’s dplyr joins report nothing, so the count has to be built by hand.

The rest of this section is mostly diagnostics.

Carrying Social Services forward

Social Services ends in 2022; our data runs to 2025. Before joining, we give every ZCTA rows through 2025 and carry its most recent values into them. That is a decision, not a fix. The 2023 to 2025 rows will match, and what they match is 2022’s numbers. Write the decision into your methods, because nothing in the output will.

Socioeconomic status, on 2010 boundaries

NaNDA’s SES measures are five-year ACS estimates, so each file’s value stands for a stretch of years. NaNDA publishes two ZCTA files: 2008–2017 on 2010 boundaries and 2018–2022 on 2020 boundaries. Our crosswalk produces 2010-boundary codes, so every row joins the 2010-boundary file. The 2020-boundary file appears once, below, to show what changes if you mix them.

The limitation, stated as you would in a methods section: affluence for observations from 2018 onward is the 2013–2017 estimate, because NaNDA publishes no 2010-boundary ZCTA file for later years. Consistent boundaries were traded for currency, and the trade is written down.

2010 vs 2020 boundaries, side by side

The same join, run twice with the same crosswalked codes: once against the 2010-boundary SES file and once against the 2020-boundary file. Both runs succeed. Both match the same rows at the same rate, because most ZCTAs kept their five digits from one census to the next. What differs is the value attached to each row. The same people get a different mean affluence depending on which file was open. Nothing in either output says which run paired the codes with the boundaries they were drawn for. Only you can know that, from the documentation of each input.

WarningMatch the boundaries, and say which ones you matched

Every code in a join follows the boundaries of one census year: the codes in your file, the codes the crosswalk produces, and the codes the NaNDA file is drawn on. All three have to agree. Ours agree on 2010. If your data run past 2019 and you want 2020 boundaries instead, use a crosswalk that produces 2020 codes and the 2020-boundary NaNDA files, and state the choice in your methods. What you cannot do is let the file that happens to be open decide.

Three reasons appear, and they call for different responses:

  • No ZIP is the big one and a data-collection problem. Nothing downstream fixes it.
  • ZIP not in the crosswalk is a typo or a ZIP newer than the crosswalk.
  • ZCTA not in the NaNDA file usually means the two were drawn on different boundaries.

At two rows apiece the last two vanish inside a match rate. In real data they are the rows telling you something upstream is misaligned, which is why the table lists reasons and not just a count. The fourth reason, year past coverage, is absent only because we carried Social Services forward. Without that step, 407 rows would sit in that line. Either way it is a limit of the NaNDA file, handled by a decision you state in your methods. If the reasons table shows anything beyond what Section 3 already explained, run the who-did-you-lose comparison again on in_nanda.

TipFour questions to ask before every link
  1. What location information do my data contain? An address, a ZIP code, a Census code?
  2. Which census year’s boundaries do my codes follow, and which does the NaNDA file follow?
  3. Which crosswalk did I use, and which boundaries does it produce?
  4. How many rows matched, and do the unmatched rows look different from the rest?

5. Now what?

About 4 minutes, then questions

Everything above is the how. Grace Noppert closes with a few minutes on the why. Your data plus NaNDA data, joined on one geographic identifier, is a file that can answer questions neither could alone. The three measures we attached today each open one:

  • Social connection. Do older adults near more social services report less loneliness?
  • Physical activity. Is park access tied to staying active with age?
  • Food security. Does neighborhood disadvantage shape who goes without a hot meal?

None of these is answerable from a survey alone, and none from NaNDA alone. Two cautions:

  • A neighborhood measure describes a place, not a person. Be clear when it is context and when it is standing in for exposure.
  • People in the same ZCTA are not independent observations. The analysis has to account for that.

If one of these questions is close to yours, NaNDA has the measure and the catalog is where to start.
